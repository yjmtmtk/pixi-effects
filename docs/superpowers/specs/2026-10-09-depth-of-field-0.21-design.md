# 0.21 奥行き（被写界深度とピント送り）— 設計メモ

状態: **承認待ち**（オーナーのレビュー前。承認されるまで計画も実装も書かない）。
読む人: オーナー。決めてほしいことは 8 章（私の推し付き）。共通のパラメータルールとの突き合わせは 4.2。
前提: 0.20.0 まで公開済み。試作 B（`docs/superpowers/spikes-0.21-0.22/depth-of-field/`、`spike.patch` と `DiscBlur.ts`）は捨てる前提の試作で、この版では**書き直す**（試作のコードは参考にするだけ）。
ロードマップの順番はオーナーが確認済み（0.21 奥行き → 0.22 光と色）。

## 1. 目的

何でも作れるようにする、の中で、「カメラ」はあるのに**ピントがない**。いまは次ができない。

- 手前の物にピントを合わせて、奥をぼかす（映画的な浅い被写界深度）。
- **ピント送り**（手前から奥へピントを移す）。
- ぼけの量を「カメラの設定」として一か所で決める（層ごとに `blur` を手で書き分けない）。

今できる回避策は、層ごとの `blur` に奥行きから計算した値を手で入れること。カメラが動くと破綻する。

やらないこと: 光学的に正しい被写界深度（絞り形状のボケ、玉ボケの輝点強調、前ボケと後ろボケの非対称）、1 枚の層の中での奥行き変化（傾いた床）、ぼけのレイヤー間のにじみ込み（後ろの層に前の層のぼけが広がる）、`threeD` でない層へのぼかし（そのまま鮮明）。

## 2. 確かめた事実

試作 B（M1 Pro、1920×1080、1 フレームの ms、ぼかす層 5 / 20 / 60 枚）。GPU を他と共有していたため ±15% の誤差がある。

| 方式 | WebGPU | WebGL |
|---|---|---|
| ぼかし 0 枚（基準） | 6.1 | 9 |
| Pixi 標準のぼかし（品質 4） | 9 / 25〜30 / 135〜144 | 9.5〜10 / 14〜16 / 28 |
| 円盤状のぼかし（48 タップ、試作で書いた版） | 8 / 12 / 55 | 9 / 10 / 13.6 |

- **コストは、ぼけの強さによらず、フィルタを付けた層の枚数で決まる。** ぼけがほぼ 0 の層にはフィルタを付けないので、使わない人のコストは 0。
- 3〜8 面程度のピント送りなら、約 +1〜5 ms。
- 見た目: 標準のガウスぼかしはソフトフォーカス寄りで、強いと軽い二重像が出る。円盤状は縁がくっきりしていて、ボケらしい。**円盤の方が速くて見た目もよい。**
- シークの前進・ジャンプ・後ろ向き、モーションブラーの副フレームで、ピクセルが一致した（時間の決定性は守られる）。
- `blendMode`、層の `filters`（ドロップシャドウ）、入れ子の合成層とは問題なく組み合わさる。
- 弱点: ぼけは**層の原点の奥行きだけ**で決まり、1 枚の層の中では一様。傾いた床のような「1 枚の中で奥行きが変わる」層は、1 つの値になる。
- 未検証: 外付け GPU、他のブラウザ、ソフトウェア GL、4K 出力、実際の書き出し経路（`render.mjs`）、spring や式で動かす焦点、`hideBehindCamera` との併用、層名をキーフレームの `to:` に書く解決。**計画の最初の手順で、これらを実機で確かめる。**
- 別件の既存不具合（この版の変更とは無関係）: `threeD` 層が 4000×2400 だと WebGPU で黒く描かれる。ぼかしの余白（padding）で層のテクスチャが大きくなるので、この版のリスクにも関係する（7 章）。

## 3. 設計

### 3.1 書き方

カメラに 2 つの項目を足す。**`focus`**（ピントを合わせる奥行き）と **`aperture`**（絞り。大きいほど浅い＝ぼけが強い）。普通のカメラ項目なので、`initial` とキーフレームで動かせる。

```json
{ "type": "camera", "initial": { "focus": "title" } }
```
`title` という名前の層にピントが合い、ほかの `threeD` 層は奥行きの差だけ柔らかくぼける。`aperture` は書かなくてよい（既定 30）。

```json
{ "type": "camera", "initial": { "focus": "front", "aperture": 60 },
  "keyframes": [{ "at": 1, "to": { "focus": "back" }, "duration": 1, "ease": "power2.inOut" }] }
```
`front` から `back` へのピント送り。

数で書く場合は `focus: 250`（z = 250 の面にピント）。

規則（少なく、全部 1 行で言える）:

1. **`focus` は層の名前か、z の数。** 名前は、その層の**最初の z**（`initial` の `z`）に、ビルド時に解決される。数の `focus` は式の文字列でも書ける（`"GW/2"` のような既存の式）。
2. **カメラに `focus` か `aperture` が書いてあるとき、ぼかしが有効。** どちらも書いていなければ、今までどおり（コスト 0、絵も変わらない）。
3. **`aperture` を書かなければ 30。`focus` を書かなければ z = 0 の面**（`fov` だけ動かしても 1:1 のまま止まる面）。`aperture: 0` はぼかしなし。
4. **ぼけの量は、層の原点の奥行きとピント面の距離で決まる。** ピント面の層は鮮明。1 枚の層の中では一様。
5. **ピント送りに名前を使うときは、キーフレームの `to:` にも名前が書ける**（ビルド時に数へ解決。試作で未検証のため、手順 1 で確認し、使えなければ 3.3 の警告で数を案内する）。
6. `threeD` でない層は、ぼけない（AE と同じで、2D 層は被写界深度の対象外）。

`aperture` の数の意味は直感的でない（試作の弱点）。次の形で補う（細部は手順 2 で、絵を見て決める）:

| `aperture` | 見え方の目安 |
|---|---|
| 0 | ぼけなし |
| 10 | かすかに柔らかい |
| 30（既定） | はっきりした浅い被写界深度 |
| 60 | 強い（背景が大きくとける） |
| 100 以上 | 極端 |

この表は、絵を見て決める。文書には、数と同じ並びで**ぼけの大きさ（px）の例**と、4 枚の層（近・中・遠）を並べた作例の画像リンクを付ける。

### 3.2 仕組み

- 試作の流れを引き継ぐ。`Composition.updateSpace` が、カメラの `focus` から**ピント面の深度** `s` を出し、`threeD` 層ごとに奥行き `d` との差から**ぼけ量**（錯乱円の大きさ）を出して `Layer3D.setBlur()` に渡す。ぼけ量 = `aperture × カメラの焦点距離 × |1/d − 1/s| × 画面の大きさに対する係数`。ぼけ量が 0.05 px 未満の層は**フィルタを外す**（コスト 0 を守る）。
- 数式は `src/space/` の純粋関数 1 つ（`circleOfConfusion(…)`）に出して、単体テストで表と照らす。
- ぼかしフィルタは**円盤状**（`src/filters/` に `DiscBlur`、WebGL と WebGPU の両方のシェーダー）。試作では 48 タップ固定。層のぼけ量に応じた余白（padding）を足して、縁が切れないようにする。`blendMode` はフィルタ側へ移す（試作でそうした）。
- フィルタは `Layer3D.display`（射影したメッシュ）に付ける。層自身の `blur` や `filters` は射影の前の `target` に付いているので、**独立して重なる**（両方が見える）。
- 名前の解決は、ビルド時に、同じ合成の中の `threeD` 層の初期 z から。見つからない・`threeD` でないときは警告（3.3）。
- 入れ子の合成層は、**親のカメラから見て 1 枚の層として**ぼける（中身は子のカメラで、別に描かれる）。これは仕様として文書に 1 行書く。

### 3.3 警告（すべて「警告を出して、無視」。書き方の間違いは作るときに 1 回だけ言う）

`layerKeys`（`src/core/layerKeys.ts` の表）と `src/space/lint.ts` に載せる。直し方つき。

| 間違い | 警告の内容 |
|---|---|
| `focus: "tilte"`（存在しない名前） | 「focus: 層 "tilte" が見つかりません。もしかして "title"？」（did-you-mean） |
| `focus` が `threeD` でない層を指す | 「層 "label" は threeD ではありません。focus は threeD 層の名前か、z の数で書いてください」 |
| `focus` の名前の層の z が動く（`z` のキーフレームがある） | 「focus は "title" の最初の z しか見ません。ピントを動かすなら、focus のキーフレームを数で書いてください」 |
| `aperture` を書いたが `threeD` 層が 1 枚もない | 「この合成に threeD 層がないので、aperture は何も変えません」 |
| ピント面がカメラの後ろ（`s ≤ 0`） | 「focus がカメラの後ろです。カメラの前（z がカメラより小さい側）に置いてください」 |
| 同時にぼける層が多い（**20 枚以上**） | 「ぼける層が N 枚あります。1 枚ごとに描画が 1 回増えます（WebGPU は特に重い）。遠い層をまとめるか、aperture を下げてください」 |
| 別名: `depthOfField` / `dof` / `focalDistance` / `focusDistance` / `fStop` / `blurAmount` | 「`focus`（ピント面）と `aperture`（絞り）を使ってください」（`COMMON_ALIASES`） |
| カメラが複数あって `focus` が違う | 既存の「カメラの重なり」警告と同じ扱い（最後に書いたカメラが勝つ） |

警告の総数は、`noFalseWarnings` の既存の例（ギャラリー全作品）で**ゼロ**のままであること。

### 3.4 `inspect`

AI が「ピントが合っているか」を確かめられるように、`movie.inspect(frame)` の `threeD` 層の行に、そのフレームでの**ぼけ量（px）**を足す。ピント面の層は 0、遠い層は大きい値。`review()` は、**ピント送りの前後で、その層のぼけ量が変わっている**ことを 1 行で報告する（形は計画で、既存の行に合わせる）。キャプチャーのコンタクトシートでも、ぼけは絵に出る。

## 4. AI 親和性と、共通のパラメータルールとの整合

### 4.1 AI 親和性

| 観点 | 判定 |
|---|---|
| 共有の語彙 | `focus` / `aperture` は普通のカメラ項目で、`initial`、キーフレーム、`ease`、spring、`repeat`、式が、そのまま使える。新しい小さな言語はない |
| よくある使い方は 1 行 | `{ "type": "camera", "initial": { "focus": "title" } }` |
| 間違いは作るときに直し方つきで警告 | 3.3 の表。名前の打ち間違いは did-you-mean |
| 隠れた規則 | 3 つ: (a) 名前は最初の z、(b) ぼけは層の原点の奥行きで一様、(c) 入れ子の合成は 1 枚として。すべて警告か文書の 1 行で見える |
| 使わない人へのコスト | 0（`focus` も `aperture` も書かなければ、今までの道。フィルタは付かない） |

### 4.2 共通のパラメータルールとの整合

| 共通ルール | 新しい名前の扱い |
|---|---|
| 全層で同じ語彙。新しい小さな言語を作らない | `focus` / `aperture` はカメラの普通の項目。層名で指すのは、既存の名前参照（層の `name`、シーン名）と同じ種類 |
| 数は式の文字列でも書ける（ビルド時のみ） | 数の `focus` と `aperture` は式が書ける。名前は文字列そのままで解決 |
| 動く値は `initial` とキーフレーム、固定の設定は最上位 | 両方とも動く値なので `initial` とキーフレーム（最上位ではない） |
| 長さの単位は px、奥行きは z | `focus` の数は z と同じ単位。`aperture` は単位のない係数（`scale` と同じ種類）で、表で px の目安を示す |
| 名前の意味は 1 か所で決まる | 層の `blur`（その層の自己ぼかし）と、カメラ由来のぼけは別。文書に 1 行: 「`blur` = 自分で決めるぼけ。`aperture` = 奥行きから自動で決まるぼけ」。重ねがけになる |
| 打ち間違い・別名は直し方つきの警告 | 3.3。`CAMERA_PROPS` と `PROP_KEYS` に足すと、`Covers` 型がビルドで表の更新漏れを教える |
| エンジン中立の名前（`docs/philosophy.md` の「Engine names」） | `focus` / `aperture` は仕様の言語の名前で、ぼかしの実装（2.5D の層ごとの円盤ぼかし）には依存しない。将来、主エンジンが本物の深度ポストエフェクトを持てば、**同じ 2 つの名前を、同じ見え方の目安で**実装に付け替えられる。エンジンの名前を含む名前は作らない（`EngineNames.test.ts` で守られる） |

## 5. テスト

- **単体（速い）**: `circleOfConfusion` の表（ピント面で 0、遠いほど大きい、`aperture` に比例、カメラの後ろで無効）、名前の解決（初期 z、見つからない、`threeD` でない）、警告 8 種（did-you-mean を含む）、`aperture: 0` と未指定でフィルタが付かないこと、`PROP_KEYS` の網羅。

- **既存への影響**: カメラに `focus` / `aperture` を書かない既存の作品は、**ピクセル一致**（ギャラリーの `threeD` を使う作品で比較）。
- `scripts/test-changed.mjs` の領域に、新しいファイルを追加して、`test:changed` が必要なブラウザテストを選べるようにする。

## 7. リスク

- **WebGPU は 1 枚あたりの負担が大きい**（試作で 0.8〜2 ms）。60 枚で 55 ms。警告（20 枚）と文書で知らせる。
- **余白（padding）で層のテクスチャが大きくなる。** 既存の不具合（4000×2400 の `threeD` 層が WebGPU で黒い）に当たりうる。手順 1 で確かめ、ぼけ量の上限か、余白の上限を決める。
- ぼけは**層の原点の奥行きだけ**。床のような層は一様にぼける。文書に書く。気になる作品は層を分ける。
- 名前の解決を「最初の z」にしたことで、動く層に `focus: "name"` と書くと、追従しない。警告で案内（3.3）。将来、追従したくなったら、別の名前（例: `focus: { follow: "name" }`）で足せる。いま作らない。
- 円盤ぼかしは 48 タップ固定。強いぼけで縞が見える可能性がある。手順 3 で絵を見て、必要ならタップ数を `aperture` に応じて変えるか、ノイズでずらす（時間に依存しない形で）。
- 外付け GPU、他のブラウザ、ソフトウェア GL は未検証。書き出しの経路は手順 1 で確かめる。

## 8. 決めてほしいこと（私の推し付き）

1. **ぼかしは最初から円盤状だけにする（ガウスは作らない）。** 速くて見た目がよく、選ばせる項目も増えない。工数は約 20 時間の見込み（試作の見積もりはガウス版 16 + 円盤 +6 時間。ガウスを作らない分だけ減るが、シェーダーが WebGL / WebGPU の 2 本ぶんなので大きくは減らない）。
2. **`focus` の名前は最初の z に解決する。** 追従は作らない（7 章）。
3. **`aperture` の既定は 30、`focus` の既定は z = 0 の面。** `aperture: 0` で切る。
4. **ぼけ量は層の原点の奥行きだけで決める。** 1 枚の中の勾配は作らない。
5. **同時にぼける層が 20 枚以上で警告。**
6. **`threeD` でない層はぼけない。**
7. **ギャラリーに「ピント送り」を 1 本付ける。**

## 9. このあとのロードマップ（案）

- 0.22「光と色」: CSS 名のブレンドモード 18 種（自前のブレンドフィルタ、約 12 時間）。
- その後: シェーダー層、ルマワイプ、フレームごとの式（`t`）、Lottie、マスクの共有・複数。
- 別件（どの版で直すか未定）: `maskInverted` とブレンドモードの併用が壊れる。`threeD` 層が 4000×2400 だと WebGPU で黒く描かれる（この版の手順 1 で原因を調べる）。
