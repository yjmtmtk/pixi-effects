# AGENTS.md — if you were asked to make a video with this repository

The person said something like "Use https://github.com/yjmtmtk/pixi-effects to make a video: …". Do NOT read the whole repository. Follow the path that matches what you can do.

## You can run commands (a shell, Node 22, Chrome): Claude Code, Codex, Cursor, …
0. If your agent supports skills, `npx skills add yjmtmtk/pixi-effects` installs this whole workflow (it is `skills/pixi-effects/SKILL.md`; steps 1–5 below are the same). Inside THIS repository (or when `npx` fails or prints nothing: `npm i pixi-effects` and use `node node_modules/pixi-effects/ai/tools/…`) the tools run as `node ai/tools/check.mjs`, `render.mjs` and `view.mjs`.
1. Read `skills/pixi-effects/reference/quickstart.md` (2 KB), then `skills/pixi-effects/SKILL.md` (the workflow and the rules that cause most failures). For anything else ask the docs instead of reading them: `npx pixi-effects help <word>` prints the sections about a word, `npx pixi-effects recipe [id]` lists the tested recipes and prints one with its code (inside THIS repository: `node ai/tools/pixi-effects.mjs help <word>`). `skills/pixi-effects/reference/cheatsheet.md` and `pitfalls.md` are for looking things up, not for reading end to end.
2. Start from the template: `npx pixi-effects new my-video` writes `my-video.html` next to the person's work (or copy `skills/pixi-effects/template.html`), then edit the composition. It loads the released library from a CDN, so the file works from any folder (no install needed).
3. A video is plain data: a tree of plain objects (`text`, `shape`, `image`, `audio` with `sfx` or `music`, nested `composition`s, a `camera`) with `at` / `duration` / `initial` / `keyframes`. You never write per-frame code (except inside a `canvas` layer, which you add only for a picture nothing else draws). Sound needs no files: `sfx` for effects, `music` for a tune written as text.
4. Check your work like a reviewer, in a loop: `npx pixi-effects check your-video.html` (or `node ai/tools/check.mjs your-video.html --out <a folder outside the repository>` inside this repository; it writes `check-out/<name>/` into the current folder; `--out DIR` writes straight into `DIR`, with no `<name>/` inside it). It reports library warnings (each says what to change), layout problems, sound problems and a real export; it writes a contact sheet PNG: LOOK at it (open the image) before you say you are done.
5. Export: `npx pixi-effects render your-video.html -o your-video.mp4`, or the download button in the player bar.

### If your shell is a sandbox that is not the person's computer (a browser chat's code execution: a container, often root, no GPU, a closed network)
Your commands run in a container, not on the person's computer. The person's browser has the GPU and the CDN; yours may have neither, and `check` / `render` there stalled an agent for minutes (Chrome refuses to start as root without `--no-sandbox`; with the CDNs unreachable `check` waits its whole 240 s and only says "timed out"). So **do not use the shell path above: follow the chat way below, even though you have a shell.** No `npx`, no `npm i`, no `check` / `render` / `view`:
- Take the template from CHAT.md (`raw.githubusercontent.com` is usually reachable when the CDNs are not), edit only the marked block, and give the person the whole page. The page is the deliverable; it loads the library from the CDN in the person's browser.
- **Do not render or export an MP4 in the sandbox** (no GPU: slow). The person presses the download button in the player bar: their browser exports it on their GPU, straight to their computer. Warnings reach you through the red box they paste back.
- If something stalls (a fetch, an install, a browser), **stop** after two tries: do not wrap Chrome, do not rewire the import map to local libraries. Hand the page over and say what you did not check (the picture, the sound, the warnings) so the person knows what to look at.

## You can only write text (a browser chat with no shell, no files)
Fetch https://raw.githubusercontent.com/yjmtmtk/pixi-effects/main/ai/CHAT.md and follow it. It tells you to copy `ai/chat-template.html` (one self-contained page that runs in a preview and shows every warning in a red box for the person to paste back), gives a worked example and the rules, and explains how the person gets the MP4. If your browser exposes WebMCP tools, the Playground (https://yjmtmtk.github.io/pixi-effects/examples/playground.html) offers `set_code` / `run` / `check` / `look` so you can verify your own work without a person pasting warnings back.

## Always
- Look before you claim: a contact sheet, `movie.inspect(frame)` and `movie.inspectAudio()` are built in; the library cannot tell you the video is good, only that nothing is broken.
- While you iterate, do not export the whole movie: `check --no-export --at <the moment you changed>` (seconds), `render --range 10:15` or `--scene name` for a part; one full `check` at the end.
- Ask the person only for what you cannot decide (what to show, the mood, the length); pick sizes, colours, timing and sound yourself.
- Full docs for an AI in one file: https://raw.githubusercontent.com/yjmtmtk/pixi-effects/main/llms-full.txt (the index is `llms.txt`).

## If you are changing the library itself
`npm install`, `npm run build`, then test in the order of cost: `npm run test:fast` (units, about 20 s), `npm run test:changed` (the units plus only the browser tests the changed files need; `-- --dry` says which; anything it does not know runs everything), `npm run release:check` (the whole suite, once, before a release). To see whether a change altered any picture the repository shows (the gallery and the examples), draw the pages with `node scripts/compare-frames.mjs capture --root <a tree with a built dist/> --pages <list> --out <dir>` for the old and the new tree, and `compare <dirBefore> <dirAfter>` (64 pages in about 70 s with 4 tabs, hashes first, pixels only for the frames that differ; the same build twice already differs by 1/255 on a few pages). After `npm publish`, `npm run post-publish:check` (npm, jsDelivr and only the tests that load the release from the CDN: under a minute). The real-browser tests need Chrome and a built `dist/` (rebuild after changing `src/`); they share one browser per worker, a tab per test (`PE_FRESH_BROWSER=1` starts one per test again). Read `docs/philosophy.md` first: a composition is data; every layer shares one vocabulary; time is deterministic. Docs are generated: `npm run build:ai`, `npm run guide`.
To try a page against your local build instead of the CDN, point the three `pixi-effects*` importmap entries of `skills/pixi-effects/template.html`'s copy at `../../dist/…` (right for a copy in `<repository>/examples/<your-folder>/`).
